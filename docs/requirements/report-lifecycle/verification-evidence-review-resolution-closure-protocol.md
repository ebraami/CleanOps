# Verification, Evidence Review, and Resolution Closure Protocol

## 1. Purpose

This document defines the verification and resolution-closure process for CleanStreet AI after a cleaning team completes a report.

The purpose is to make sure that a report is not closed only because a cleaning team marks it as completed. The operator must review the completion evidence, confirm that the required evidence is valid, and either approve the resolution or return the report for rework.

This protocol follows the CleanStreet AI proposal, especially the report-to-resolution workflow, completion evidence, operator review, status tracking, before/after images, timestamps, location data, and the principle that the final operational decision remains with the human operator.

## 2. Scope

This protocol applies to reports submitted by citizens and processed by cleaning teams through the CleanStreet AI platform.

It covers:

- Completion evidence submitted by the cleaning team.
- Before/after photo verification.
- Timestamp validation.
- GPS/location validation.
- Operator approval.
- Rejection and rework.
- Escalation when rework is required or delayed.
- SLA closure rules.
- Final citizen notification.
- Audit logging of verification and status changes.

Physical waste collection itself is outside the scope of the platform.

## 3. Required Completion Evidence

A cleaning team must provide completion evidence before a report can move to final resolution.

### 3.1 Mandatory evidence

The completion submission should contain:

1. At least one clear after-cleaning photograph.
2. The completion timestamp generated by the system.
3. GPS/location information for the completion evidence.
4. The report identifier linking the evidence to the original request.
5. The cleaning-team/operator identity associated with the completion action.

Where possible, the after-cleaning image should show the same area represented by the original citizen report so that the operator can compare the before and after condition.

### 3.2 Before/after evidence

The original citizen image is retained as the before evidence, while the cleaning team's submitted image is stored as completion evidence.

The operator compares the two and checks whether:

- The reported waste/problem is visible in the original evidence.
- The relevant area is visible in the completion image.
- The reported waste has been removed or the reported cleanliness problem has been addressed.
- The after image is clear enough to support the verification decision.
- The evidence does not appear to be unrelated to the report.

The proposal already defines separate image storage for the citizen image and completion evidence.

## 4. Evidence Validation Protocol

### 4.1 Photo validation

The completion photo passes the basic evidence check when:

- The image can be opened successfully.
- The relevant location/area is visible.
- The image is sufficiently clear for operator review.
- The image provides reasonable visual evidence that the cleaning action was completed.
- The image is linked to the correct report.

The system should flag missing or invalid evidence for operator attention rather than automatically declaring the report resolved.

### 4.2 Timestamp validation

The completion timestamp must be recorded with the completion evidence.

The operator checks that:

- A timestamp exists.
- The timestamp is associated with the current completion event.
- The completion event occurs after the report was created/assigned.
- An obviously inconsistent timestamp is rejected or sent for rework.

The report and assignment/completion timestamps are also used for response-time and SLA analysis.

### 4.3 GPS/location validation

The completion evidence should contain location information that can be compared with the report location.

The system should:

1. Read the completion GPS coordinates.
2. Compare them with the original report coordinates.
3. Flag evidence when the completion location is outside the configured acceptable verification area.
4. Allow the operator to review and make the final decision.

The exact distance threshold should be configurable for the pilot environment rather than hard-coded, because the proposal does not define one fixed GPS tolerance.

### 4.4 Evidence result

After validation, the evidence receives one of two operational results:

- **Accepted:** sufficient evidence is available for operator review/approval.
- **Rejected / Rework required:** evidence is missing, invalid, inconsistent, or does not demonstrate satisfactory completion.

The final decision remains with the responsible human operator.

## 5. Operator Approval Criteria

The operator may approve a completed report when all of the following are satisfied:

- Required completion evidence is present.
- The after-cleaning photo is relevant and sufficiently clear.
- The reported problem appears to have been addressed.
- Timestamp information is valid and consistent.
- GPS/location information is consistent with the report location or the operator has an acceptable operational explanation.
- There is no unresolved evidence problem.
- The cleaning team has completed the required action.

The operator must not approve a report solely because the cleaning team marked it as completed.

This follows the project rule that a report cannot be closed solely on a team completion status.

## 6. Rejection and Rework Flow

When the evidence does not satisfy the verification criteria, the operator returns the report for rework.

Typical rejection reasons include:

- Missing after photo.
- Unclear or unusable photo.
- Photo does not show the reported area.
- Waste/problem is still visible.
- Timestamp is missing or inconsistent.
- GPS/location evidence is missing or inconsistent.
- Evidence is linked to the wrong report.
- Cleaning action is incomplete.

### Rework sequence

1. Operator selects **Reject / Rework Required**.
2. Operator records the reason for rejection.
3. The report returns to the cleaning workflow.
4. The responsible cleaning team receives the rework request.
5. The team performs the required action.
6. The team submits new completion evidence.
7. The operator reviews the new evidence.
8. The report is either approved or returned for another rework cycle.

Every important status change and verification action should be recorded in the audit history.

## 7. Rework Escalation

If a report remains incomplete or is repeatedly rejected, it should be escalated according to the operational rules configured for the pilot.

Escalation may occur when:

- The team does not respond within the applicable SLA.
- The evidence is repeatedly rejected.
- The reported problem remains unresolved.
- The assigned team cannot complete the work.
- The report requires operator or management intervention.

The escalation event should be recorded with the report, timestamp, responsible team, and reason.

The exact escalation time thresholds should be configurable because the proposal does not specify fixed numerical SLA values.

## 8. SLA Closure Rules

A report must not be considered finally resolved merely because a cleaning team submits a completion update.

The report can reach final closure only after:

1. Cleaning completion evidence has been submitted.
2. Evidence validation has been completed.
3. The operator has approved the completion.
4. No required rework remains outstanding.
5. The required status change has been recorded in the status history.
6. The citizen-facing closure notification has been generated.

SLA measurements should use the recorded report, assignment, and completion timestamps.

If the configured SLA threshold is exceeded before verified completion, the system should flag the report as an SLA breach for operational monitoring.

## 9. Citizen Closure Notification

After operator approval and final closure, the citizen should receive a notification containing:

- The report reference/identifier.
- The updated resolution status.
- A short confirmation that the reported issue has been processed.
- A way to view the completion evidence where supported by the application.
- The final status/time of resolution.

The proposal specifically supports citizen status tracking, notifications, and viewing completion evidence.

If the report is returned for rework, the citizen should continue to see the report as unresolved/in progress rather than receiving a false final-closure notification.

## 10. Audit and Data Recording

The verification process should preserve an auditable record.

The following information should be retained:

- Report ID.
- Citizen report image.
- Completion evidence image.
- Evidence timestamp.
- Evidence GPS/location.
- Cleaning team.
- Operator who reviewed the evidence.
- Verification result.
- Rejection/rework reason, if applicable.
- Status changes and their timestamps.
- Completion and closure timestamps.

The existing `STATUS_HISTORY` design is used to record important status changes, while the `IMAGES` table supports multiple images including before/after evidence.

## 11. Roles and Responsibilities

### Citizen

- Submits the original report.
- Provides the original photo and location when reporting.
- Tracks the report status.
- Views completion evidence and resolution information.

### Cleaning Team

- Receives assigned work.
- Performs the cleaning action.
- Submits the required completion evidence.
- Performs rework when the evidence is rejected.

### Operator

- Reviews the report and completion evidence.
- Checks photo, timestamp, and location evidence.
- Approves or rejects the completion.
- Requests rework when necessary.
- Initiates escalation when operational intervention is required.
- Makes the final operational verification decision.

### System

- Stores evidence and report data.
- Links evidence to the correct report.
- Records timestamps and status history.
- Flags evidence or SLA conditions requiring attention.
- Sends configured notifications.

AI outputs remain decision-support information. The final operational decision is made by the human operator.

## 12. Verification Decision Summary

| Check | Required result | Action if failed |
|---|---|---|
| After photo exists | Yes | Reject / request rework |
| Photo is clear and relevant | Yes | Reject / request rework |
| Reported problem is addressed | Yes | Reject / request rework |
| Timestamp is available and consistent | Yes | Reject / investigate |
| GPS/location is available and consistent | Yes | Reject / investigate |
| Correct report/evidence linkage | Yes | Reject / correct linkage |
| Operator approval | Yes | Continue verification or rework |
| SLA condition satisfied | Yes, or breach explicitly recorded | Flag/escalate |
| Status history updated | Yes | Do not finalize closure |
| Citizen notification generated | Yes after approved closure | Complete closure process |

## 13. Relationship to the CleanStreet AI Architecture

This protocol uses the architecture already defined in the proposal:

- `REPORTS` stores the central report and its current status.
- `IMAGES` stores the original and completion evidence.
- `STATUS_HISTORY` records status changes for audit and analytics.
- `CLEANING_TEAMS` stores responsible cleaning teams.
- `ASSIGNMENTS` links reports to teams and records assignment/completion timestamps.
- PostgreSQL/PostGIS supports structured and spatial data.
- Object storage is used for images.

The verification workflow therefore connects directly to the existing report, image, status, assignment, and analytics design rather than introducing a separate system.

## 14. Verification and Closure Principle

The core rule is:

**Team completion is not the same as verified resolution.**

A report is finally closed only after the required completion evidence is available, the evidence has been checked, and the responsible operator has approved the resolution.

This preserves the CleanStreet AI principle of **AI-assisted decision support with human operator control** and supports the project's end-to-end report-to-resolution workflow.
