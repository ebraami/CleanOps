# Reports Entity Schema

**Project:** CleanOps  
**Phase:** P01 — Project Foundation & Requirements  
**Work Package:** Data Requirements  
**Entity:** `REPORTS`  
**Requirement Type:** Central Entity Schema  
**Status:** Draft

---

## 1. Purpose

The `REPORTS` entity is the central record for a citizen-submitted urban cleaning report.

It connects the original report submitted by the citizen with information later produced or managed by the system, including ownership, classification, location, prioritization, lifecycle status, and creation time.

The schema is intentionally limited to information that belongs to the report itself. AI analysis results, assignments, verification evidence, notifications, and detailed status history may be represented by related entities rather than being embedded directly into this central record.

## 2. Data Ownership Model

A report contains information from three sources:

- **Citizen / device-provided:** information supplied when the report is created.
- **System-generated:** values created automatically by the platform.
- **System-managed or computed:** values maintained or calculated as the report moves through the system.

This distinction is important because users should not be able to directly modify values controlled by the system.

## 3. Field-Level Specification

| Field | Type | Source | Required | Constraints / Requirements |
|---|---|---|---|---|
| `id` | UUID | System-generated | Yes | Primary key. Unique for every report and immutable after creation. |
| `user_id` | UUID | System-derived | Yes | Identifies the authenticated citizen who submitted the report. Must reference a valid user and must not rely on an arbitrary client-supplied identity. |
| `category_id` | UUID | Citizen-provided | Yes | References the selected report category. Must reference an existing valid category. |
| `latitude` | Decimal | Citizen/device-provided | Yes | Must represent a valid geographic latitude within the accepted coordinate range. |
| `longitude` | Decimal | Citizen/device-provided | Yes | Must represent a valid geographic longitude within the accepted coordinate range. |
| `description` | Text | Citizen-provided | Yes | Describes the reported issue and must satisfy defined length and content-validation rules. |
| `priority_score` | Numeric | System-computed | Conditional | Represents calculated report priority. Must not be directly editable by the citizen. Its scale and calculation are defined separately by prioritization requirements. |
| `current_status` | Enumerated value | System-managed | Yes | Represents the report's current lifecycle state. Must use only statuses defined by the Report Lifecycle requirements. |
| `created_at` | Timestamp | System-generated | Yes | Records when the report was created. Must be generated by the system and not directly editable by the citizen. |

## 4. Source-of-Truth Rules

### Citizen / Device Input

The following values originate from the reporting process:

- `category_id`
- `latitude`
- `longitude`
- `description`

The system is responsible for validating these values before accepting the report.

### System Identity

`user_id` is associated with the authenticated session rather than being trusted as an identity supplied by the client. This ensures that a report is associated with the account that actually submitted it.

### System-Controlled Values

The following values belong to the platform rather than the citizen:

- `id`
- `priority_score`
- `current_status`
- `created_at`

These values must be controlled by server-side application logic or database rules as appropriate.

## 5. Data Integrity Requirements

The `REPORTS` entity shall maintain the following integrity properties:

1. Every report must have a unique identifier.
2. Every report must be associated with a valid submitting user.
3. Every report must reference a valid category.
4. Location values must be valid geographic coordinates.
5. Required report information must be present before the report is accepted.
6. System-generated identifiers and timestamps must not be client-controlled.
7. Citizens must not be able to directly assign or manipulate their own `priority_score`.
8. Citizens must not be able to arbitrarily change `current_status`.
9. Status values must remain consistent with the defined report lifecycle.
10. Relationships to users and categories must remain referentially valid.

## 6. Report Creation

At report creation time, the expected data flow is:

```text
Citizen
   │
   ├── Category
   ├── Location
   └── Description
          │
          ▼
     Report Submission
          │
          ▼
      System Validation
          │
          ├── Generate report ID
          ├── Resolve authenticated user
          ├── Record creation time
          ├── Set initial status
          └── Prepare report for prioritization
          │
          ▼
        REPORTS
```

The report should only become a valid persisted entity after the required fields have passed validation.

## 7. Lifecycle Relationship

`current_status` represents the report's **current state**. The complete history of state changes should not be inferred from this single field.

The Report Lifecycle requirements should define the allowed states and transitions.

Conceptually:

```text
Submitted
    ↓
Analyzed
    ↓
Prioritized
    ↓
Assigned
    ↓
In Progress
    ↓
Pending Verification
    ↓
Closed
```

The exact lifecycle states and transition rules are maintained by the **Report Lifecycle Requirements** work package.

## 8. Separation from Related Data

The `REPORTS` table should remain focused on the core report record.

| Related Information | Reason for Separation |
|---|---|
| AI detection/classification results | AI may produce multiple results and evolve independently of the report record. |
| Cleaning assignment | A report may have assignment history and operational ownership changes. |
| Status history | A single `current_status` value cannot represent the full lifecycle history. |
| Verification evidence | Completion evidence may include files, notes, timestamps, or reviewer information. |
| Notifications | Notifications are events delivered to users and should not be treated as report attributes. |
| Report images | Images may require separate storage and metadata management. |

This separation keeps the central report entity understandable while allowing the surrounding system to grow without turning `REPORTS` into a catch-all table.

## 9. Security and Privacy Considerations

The `REPORTS` entity contains potentially sensitive information, particularly the relationship between a user and a geographic location.

Therefore:

- Access to report records must follow the system's authorization rules.
- A citizen should only be able to access reports they are authorized to view.
- `user_id` must be derived from authenticated identity rather than trusted from arbitrary client input.
- Location data should only be exposed to roles and processes that require it.
- System-controlled fields must not be directly writable by unauthorized clients.
- Changes to important report information should be auditable where required by the security and audit requirements.

Detailed security controls are defined separately under **Security Requirements**.

## 10. Open Decisions

The following details should be finalized by the related requirements before implementation:

### Priority Score

The exact scoring range, calculation formula, factors, recalculation rules, and ownership of the calculation should be defined by the **Prioritization / AI Requirements**.

### Current Status

The exact status vocabulary and valid transitions should be defined by the **Report Lifecycle Requirements**.

### Description Validation

The final minimum/maximum length and content-validation rules should be defined as part of the functional and non-functional requirements.

### Location Precision

The project should determine the appropriate precision for storing and displaying report coordinates while balancing operational usefulness with privacy requirements.

## 11. Summary

The `REPORTS` entity serves as the central record connecting a citizen's submitted issue with the system-managed lifecycle of that issue.

Its core responsibilities are to identify:

- **who** submitted the report,
- **what** was reported,
- **where** it was reported,
- **when** it was created,
- **how important** the system considers it,
- and **where it currently stands** in the operational lifecycle.

The schema deliberately distinguishes citizen-provided information from system-generated and system-controlled information. This provides a clear foundation for database design while leaving detailed AI, prioritization, lifecycle, security, and operational behavior to their respective requirement areas.
