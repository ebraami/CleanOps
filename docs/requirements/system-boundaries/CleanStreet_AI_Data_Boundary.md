**CleanStreet AI — Data Boundary**

**What Enters vs. What’s Derived Internally**

**1\. Purpose**

This section defines the data boundary in CleanStreet AI by distinguishing external data that enters the system from data generated internally through processing, analysis, and platform logic. This clarifies which data the system is responsible for receiving and validating versus what it is responsible for computing.

**2\. What Enters the System (External Input)**

External input refers to data that originates outside the CleanStreet AI platform and is received from citizens, devices, or external services.

- Citizen-submitted photos/images (e.g., litter, illegal dumping, waste overflow).
- GPS coordinates or a map-picked location supplied with the report.
- Issue category/type selected by the citizen.
- Optional text description provided by the citizen.
- Weather conditions obtained from an external weather API/service, if used.
- External map or route data obtained from a third-party map service, if used.

**Key principle:** External data is classified by its origin. If the data is received from a citizen, device, or external service, it is an External Input.

**3\. What Is Derived Internally (Internally Derived Data)**

Internally derived data refers to information created by CleanStreet AI after it processes, transforms, analyzes, or combines external inputs.

- System-generated metadata such as Report ID, submission timestamp, and processing timestamp.
- Cleaned, normalized, encoded, or otherwise transformed data produced during preprocessing.
- Extracted image features generated by image-processing or AI components.
- AI/model-based classifications such as detected waste type or cleanliness category.
- Severity score calculated from report evidence and relevant factors.
- Priority level/ranking calculated from severity, time, location, and other defined rules.
- Distance or route calculations derived from map/location data.
- Hotspot detection based on aggregated historical reports and locations.
- Aggregated statistics and trends over time or by district/area.
- Validation flags, including invalid-location, low-quality-image, or inconsistent-report indicators.
- Duplicate-detection results identifying potentially repeated reports.

**Key principle:** Data is internally derived when the platform calculates, transforms, classifies, validates, aggregates, or otherwise generates it from available inputs.

**4\. Data Boundary Classification Rule**

Data is classified based on its origin and how it is produced. Data received from citizens or external services is considered **External Input**, while data calculated, transformed, classified, validated, aggregated, or generated by the platform is considered **Internally Derived**.

**5\. Delivered Means**

The required deliverable is a short document that classifies every major data type as either “External Input” or “Internally Derived.” This classification forms part of the system’s data boundary specification.

**7\. Accuracy Notes**

- External inputs are defined by origin: they come from outside users, devices, or services.
- Internally derived data is defined by processing: it is created by platform computation, transformation, analysis, or logic.
- External map data remains external even if the platform uses it for calculations; the resulting distance/route values are internally derived.
- A citizen-provided category is external input, while a category predicted by an AI model is internally derived.
- The same original input can therefore lead to multiple internally derived outputs after processing.

**8\. Final Data Flow**

**External Sources → Raw Inputs → Internal Processing → Derived Data → Analytics / Decision Support**
