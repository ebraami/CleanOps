# Data Privacy, Anonymization, and Storage Access Policy

## 1. Purpose and Scope

### 1.1 Purpose

This document defines the privacy safeguards for citizen submissions in CleanStreet AI. It specifies:

1. How reporter identities are **anonymized and masked** (PII masking).
2. How report coordinates are **coarsened and jittered** before appearing in any public-facing view (GPS obfuscation).
3. How **citizen contact details** are protected.
4. How **media objects** (report photos and completion evidence) are stored **private by default** and accessed only through **expiring signed URLs**.

The goal is that a citizen can report a waste problem without exposing who they are, where they live or move, or who and what appears in their photos.

### 1.2 Why this matters for CleanStreet AI

Every report contains a photo, a GPS location, a category, and an optional description (Proposal, Section 2). Because the GPS location is captured at the moment the citizen submits the report, it also approximates **where the reporter physically was**. Photos of public streets can contain identifiable people, vehicles, and addresses (Proposal, Section 17). Reports are therefore treated as personal data, not only as operational data.

### 1.3 Scope

This policy applies to:

- The citizen mobile application, the cleaning-operations dashboard, the backend REST APIs, the AI service, PostgreSQL/PostGIS, and object storage (Firebase Storage or Amazon S3).
- All environments (development, testing, pilot, production).
- All people and services that touch the data: citizens, operators, cleaning-team members, the AI service, and anyone holding an administrative role.

### 1.4 Out of scope

- Authentication mechanics and the definition of roles and permissions. These belong to **T_85ab37 (Authentication & RBAC Specification)**. This document defines the **data-level rules** that sit on top of it and does not redefine roles.
- Physical security, network architecture, and municipal system integration (the Proposal defines the MVP as a standalone platform).

## 2. Definitions

| Term | Meaning |
|---|---|
| **PII** | Information that identifies, or can reasonably be linked to, a person: name, email, phone number (if collected), account identifier, device or push-notification token, precise location tied to a user, free-text that contains such details, and images showing identifiable people, vehicles, or addresses. |
| **Public-facing view** | Any screen, API, map, export, share link, or embedded widget reachable without an authenticated role that holds the corresponding permission under T_85ab37. For example: a public map or heatmap, public statistics, or an open-data download. |
| **Operator-facing view** | The cleaning-operations dashboard and its APIs, available to authenticated Operators and Cleaning Team members. These are **not** public, but still apply PII masking (Section 5). |
| **Precise coordinates** | The exact latitude/longitude captured with a report and stored in `REPORTS`. |
| **Public coordinates** | A coarsened (and, where specified, jittered) location derived from the precise coordinates for use in public-facing views (Section 7). |
| **Media object** | Any file in object storage: a citizen's report photo, its sanitized derivative, or a completion-evidence photo uploaded by a cleaning team. |
| **Raw original** | The unmodified file exactly as uploaded by the client. |
| **Sanitized derivative** | A copy of the original with metadata removed and faces and license plates blurred where feasible (Section 8). |
| **Signed URL** | A time-limited URL, generated by the backend after an authorization check, that grants one specific action (GET or PUT) on one specific object. |

## 3. Data Inventory and Classification

Classification maps to the data model in Proposal Section 15.2 (seven tables) and the data listed in Section 13.

| **Confidential** | Personal or potentially personal data | Role-limited access; masked in operator-facing views where not required |
| **Internal** | Operational data with no direct personal data | Authenticated access only |
| **Public (derived)** | Coarsened, aggregated data produced under this policy | May appear in public-facing views |

| `REPORTS.category_id`, `priority_score`, `current_status`, `created_at` | PostgreSQL | Internal | |
| `IMAGES.storage_url` | PostgreSQL | Restricted | Holds a private object reference only (rule MED-6) |

It does not collect contacts, microphone audio, background location, or any data unrelated to reporting.

## 4. Roles and Data Access

The human roles used here are the ones defined in **T_85ab37 (Authentication & RBAC Specification)**: **Citizen**, **Operator**, **Cleaning Team member**, and **Administrator**. The **AI service** is a non-human service identity. T_85ab37 is the authority on how roles are issued and enforced; this section adds the **data-level** rules on top of it. As in T_85ab37, "within scope" means restricted to the user's assigned scope and authorized records, and holding a role never bypasses authentication or authorization controls.

### 4.1 Access matrix

| Data | Citizen | Operator | Cleaning Team member | Administrator | AI service | Public visitor |
|---|---|---|---|---|---|---|
| Reporter name / email / contact | Own only | **No** | **No** | Only for user management, logged | **No** | **No** |
| Own report history and status | Own only | n/a | n/a | n/a | n/a | No |
| Precise coordinates | Own reports | Reports within their authorized operational scope | Assigned reports only | **No** | Server-side computation only; never returned to a client | **No** |
| Public (coarsened) coordinates | Yes | Yes | Yes | Yes | n/a | Yes |
| Free-text description | Own reports | Yes, within scope | Assigned reports, only as required for the work | **No** | **No** | **No** |
| Sanitized photo | Own reports | Yes, within scope | Assigned reports | **No** | Read-only | **No** |
| Raw original photo | **No** (they already hold it on their device) | Only accounts holding an explicit raw-media permission, with logged justification | **No** | **No** | **No** | **No** |
| Completion evidence | Own reports (to confirm resolution) | Yes, within scope (verification and evidence review) | Upload and view for assigned reports | **No** | Read-only if required for verification features | **No** |
| Audit / security records | **No** | **No** | **No** | Authorized records only | **No** | **No** |
| Aggregated public statistics | Yes | Yes | Yes | Yes | n/a | Yes |

### 4.2 Principles

- **Least privilege and need-to-know.** Access is granted by role and by object (ownership or assignment), never broadly.
- **Server-side enforcement.** Every access decision is made by the backend. Clients never receive credentials that grant direct database or storage access.
- **Ownership checks.** A citizen can only reach media and data of reports where `REPORTS.user_id` equals their own ID. Cleaning Team members can only reach reports linked to their team through `ASSIGNMENTS`.
- **No shared accounts** for any role that can see Restricted or Confidential data.
- **Administrator access is bounded.** Administrators manage users, role assignments, system configuration, and security settings (T_85ab37, Section 10). They see account details only to perform user management, and they receive no routine access to report media or precise coordinates. Their access is authenticated, authorized, and logged, and administrative privilege does not bypass these rules.
- **Privacy parameters are configuration.** Changes to the values in this document (grid sizes, k-threshold, signed URL lifetimes, retention periods) are administrative configuration changes and are audit-logged (Section 12).

## 5. PII Masking and Reporter Anonymization

### 5.1 Public-facing views

Public-facing views never reveal who reported. Field-level treatment:

| Field | Treatment in public-facing views |
|---|---|
| Reporter name, email, contact details | **Never shown** |
| `user_id` or any identifier derivable from it | **Never shown.** No per-user pseudonym is displayed, because a stable pseudonym would let a viewer link one person's reports and infer where they live or travel. |
| Reporter label | A constant label such as "Citizen report" |
| Report identifier | A random, non-sequential **public reference** with no mathematical relationship to the internal ID (prevents enumeration and cross-referencing) |
| Description | **Not shown** |
| Photos (original, sanitized, evidence) | **Not shown** (see MED-9 for any future public gallery) |
| Location | Public coordinates only (Section 7) |
| Timestamps | Date only; week precision for sensitive-tier reports (Section 7.4) |
| Category and status | Shown (status values such as acknowledged / in progress / resolved) |
| `priority_score` | Not shown (internal operational data) |
| Counts and hotspots | Aggregated, with small-cell suppression (Section 7.5) |

### 5.2 Operator-facing views

Operators and cleaning teams need the report content, not the reporter's identity (Proposal Section 16.2 workflow: review image, location, category, AI results, assign, monitor, review completion).

- **PII-1.** Operator-facing and cleaning-team APIs and dashboards **omit** `USERS.name`, `USERS.email`, and `user_id` from report responses. They identify a report by its report reference, not by its reporter.
- **PII-2.** Duplicate and hotspot detection (Proposal Section 11, Tier 3) run **inside the database/backend** on precise coordinates and embeddings. Their outputs shown to operators are report links and counts, not reporter details.
- **PII-3.** Reporter identity is only resolved by the backend for authentication and for sending the citizen's own notifications.

### 5.3 Free-text descriptions

- **PII-4.** Descriptions are shown only to the owning citizen, Operators, and the assigned team (matrix 4.1) and never in public views.
- **PII-5.** Any dataset, analytics export, or AI evaluation set built from reports **excludes the description field**, unless it first passes automated PII scrubbing (emails, phone numbers, long digit sequences resembling ID numbers, and URLs masked) and review.
- **PII-6.** The report submission screen warns citizens not to write names, phone numbers, or home addresses in the description (Section 11).

### 5.4 Logs, errors, analytics

- **PII-7.** Application logs, error traces, and analytics events **must not contain** names, emails, precise coordinates, descriptions, push tokens, or signed URLs. Where an identifier is unavoidable it is the opaque internal ID, never a name or email.
- **PII-8.** Third-party services receive no user identifiers. The Google Maps Routes API receives only the coordinates needed for route calculation, sent from the backend. OpenWeather receives coordinates rounded to two decimal places (about 1 km), which is sufficient for weather context.

## 6. Citizen Contact Protection

- **CP-1.** A citizen's email (and phone number, if ever collected) is visible only to that citizen and to the authentication and notification subsystems. It never appears in operator dashboards, cleaning-team views, exports, public views, or logs.
- **CP-2.** The platform communicates with citizens on behalf of operators (status updates, completion notices). Operators and cleaning teams never see or copy contact details. If a clarification channel is added in future, it is relayed through the platform in-app.
- **CP-3.** **Notification payloads** (Firebase Cloud Messaging) contain only a report reference and a status text. They never contain precise location, description, image content, or a media URL, because notification text can appear on a locked screen.
- **CP-4.** Push tokens are bound to the owning account and removed on logout and on account deletion.
- **CP-5.** Contact details are never sold, shared for advertising, or given to third parties other than the services strictly required to deliver the platform (authentication and push notifications).
- **CP-6.** Citizens can delete their account and contact details (Section 10.3).

## 7. GPS Coordinate Obfuscation Rules (Public Views)

### 7.1 Principle

Precise coordinates are required **internally**: routing, PostGIS duplicate detection (distance/time pre-filter), and `ST_ClusterDBSCAN` hotspot detection (Proposal Sections 11 and 15). They are **never** published. Public-facing views use coordinates derived under this section.

### 7.2 Rules

- **GPS-1.** Precise coordinates appear in no public-facing API response, map tile, export, share link, push notification, or log.
- **GPS-2.** **Public coordinates are computed once** (at report creation, and again only if the tier changes) and **stored** as derived fields. They are **not** recalculated per request. A fresh random offset on every request would let an observer average repeated responses and recover the true point.
- **GPS-3.** Public views are **cell-based by default**: reports are shown as counts per grid cell, not as individual points.
- **GPS-4.** Public APIs offer **no nearest-neighbour, radius, or distance queries** on precise data, return no distances, and do not sort results by distance from a supplied point. This prevents trilateration of a hidden location. Public queries run against public coordinates only (for example, by bounding box on the grid).
- **GPS-5.** Public responses never include more coordinate precision than the cell centroid or displaced point they represent (no trailing digits that leak the original).
- **GPS-6.** Exports and analytics datasets use public coordinates or cell IDs. Precise coordinates stay inside the controlled backend environment.
- **GPS-7.** Photo metadata that carries GPS (EXIF) is removed from every stored derivative (Section 8), so location cannot leak through the image.

### 7.3 Derivation of public coordinates

Computed in a metric (projected) coordinate system, for example with PostGIS `ST_SnapToGrid` after transforming to a projected CRS, so that cell sizes are in metres.

| Tier | When it applies | Coarsening | Jitter |
|---|---|---|---|
| **P1 — Standard** | Default for all reports | Snap to a **250 m** grid cell; publish the cell identifier and centroid | None for cell aggregates. If an individual marker is ever shown, it is placed at the cell centroid plus a **deterministic offset kept inside its own cell** |
| **P2 — Sensitive** | See 7.4 | Snap to a **1 km** grid cell | Individual markers **disabled**; aggregate only |

**Deterministic jitter.** Where a marker offset is used, it is derived from `HMAC-SHA256(secret_key, public_reference)`: the same report always gets the same offset, the offset never moves the point outside its cell, and the secret key is stored server-side (secrets manager) and never shipped to clients. The offset prevents markers from stacking on the centroid and from revealing the grid structure.

### 7.4 Sensitive-tier triggers (P2)

A report is placed in tier P2 if **any** of the following is true:

1. The sanitization step detected faces, license plates, or readable text or addresses in the image.
2. The surrounding area is sparse: fewer than **k = 3** other reports fall within 1 km, so a 250 m cell could correspond to a handful of households.
3. An operator manually flags the report as sensitive.

For P2 reports, public timestamps are reduced to **week** precision.

### 7.5 Small-cell suppression

A public cell is shown only if it contains **at least k = 3 reports**. Cells below the threshold are merged into the parent 1 km cell, or hidden if that cell is also below the threshold. The public heatmap is built from grid aggregates, not from raw `ST_ClusterDBSCAN` centroids.

### 7.6 What citizens and operators see

| Viewer | Location shown |
|---|---|
| Report owner | Their own report's precise location |
| Operator (jurisdiction) | Precise location (needed to assign and review) |
| Assigned cleaning team | Precise location for assigned reports only |
| Public visitor | Public coordinates / cell aggregates only |

## 8. Media Handling and Sanitization Pipeline

Applies to both citizen report photos and cleaning-team completion evidence (`IMAGES.image_type`: before / after).

### 8.1 Pipeline

1. **Request upload.** The client asks the backend for an upload permission. The backend authenticates the user, checks their role, and returns a short-lived signed **PUT** URL for a new random object key in `raw/` (Section 9.4).
2. **Upload and validation.** The client uploads directly to storage. The backend validates file type (by content, not by extension) and size (limit configurable; default 10 MB). Failed validation deletes the object.
3. **Sanitization.** A processing job (a) **strips all metadata** (GPS, device model, timestamps, owner) by re-encoding the image, and (b) applies **automated face and license-plate blurring where feasible** (Proposal Section 19, Privacy risk). The result is written to `processed/` (or `evidence/` for completion photos).
4. **AI analysis.** The AI service reads the **sanitized derivative** and writes its results (priority score, category) back to PostgreSQL (Proposal Figure 4).
5. **Reference.** `IMAGES.storage_url` points to the stored object (rule MED-6).

### 8.2 Rules

- **MED-1.** Metadata is removed from every derivative; no original EXIF is ever served to any role.
- **MED-2.** Blurring is applied automatically and **where feasible**. It is a risk-reduction control, not a guarantee, so the other controls (private storage, role limits, retention) do not depend on it.
- **MED-3.** If blurring cannot run or its confidence is low, the report is still accepted and processed, the report is marked for the sensitive tier (Section 7.4), and the issue is recorded for review. Reporting is not blocked.
- **MED-4.** The raw original is accessible only to the sanitization job and, for quality review, to Operator accounts holding the explicit raw-media permission (Section 4.1). Every raw access is logged (Section 12).
- **MED-5.** Raw and processed copies share the same random object ID (for example `raw/<object_id>` and `processed/<object_id>`), so `IMAGES.storage_url` needs no extra column.
- **MED-6.** `IMAGES.storage_url` stores the **internal object reference only** (bucket path/key). It never stores a signed URL, a Firebase download-token URL, or any public link.
- **MED-7.** Object keys are random (UUIDv4), contain no PII, and encode no user, report, location, or time information.
- **MED-8.** Completion evidence goes through the same sanitization pipeline.
- **MED-9.** Public-facing views do not serve media. If a public before/after gallery is added in future, it may only use sanitized derivatives approved by an operator, served through short-lived signed URLs, and the report owner must be informed.

## 9. Private Storage Bucket Access Policy

### 9.1 Default posture

**Deny by default.** No media object is publicly readable, listable, or writable. All access goes through backend-issued signed URLs or through service identities with narrowly scoped permissions.

### 9.2 Bucket configuration requirements

- **BKT-1. Private by default.**
  - *Amazon S3:* enable **Block Public Access** (`BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, `RestrictPublicBuckets`) on the bucket and at account level; disable ACLs with Object Ownership set to **BucketOwnerEnforced**.
  - *Firebase Storage:* security rules deny all direct client access; the backend uses the Admin SDK (which is not subject to client rules) to issue signed URLs:

    ```
    rules_version = '2';
    service firebase.storage {
      match /b/{bucket}/o {
        match /{allPaths=**} {
          allow read, write: if false;
        }
      }
    }
    ```
- **BKT-2. No long-lived links.** Firebase "download URLs" created with `getDownloadURL` carry long-lived tokens that act as permanent bearer links. They **must not be issued or stored**. Only backend-generated signed URLs (V4) with the lifetimes in Section 9.4 are allowed.
- **BKT-3. Separated areas and identities** (separate buckets or prefixes with separate permissions):

  | Area | Contents | Who can read | Who can write |
  |---|---|---|---|
  | `raw/` | Raw originals | Sanitization job; backend signing identity for authorized raw-media requests | Citizens via signed PUT (own uploads) |
  | `processed/` | Sanitized report photos | Backend signing identity (for GET URLs); AI service | Sanitization job only |
  | `evidence/` | Sanitized completion evidence | Backend signing identity (for GET URLs); AI service if required | Cleaning teams via signed PUT; sanitization job |

  Clients (mobile app, dashboard) hold no storage credentials. The AI service has **read-only** access to `processed/` (and `evidence/` if needed) and no access to `raw/`.
- **BKT-4. Encryption.** Encryption at rest with provider-managed keys (customer-managed keys where available), and encryption in transit with TLS 1.2 or higher. The S3 bucket policy denies requests where `aws:SecureTransport` is false.
- **BKT-5. Non-guessable keys.** Random UUIDv4 object keys (MED-7).
- **BKT-6. CORS** restricted to the application's own origins and only to the methods needed (GET, PUT).
- **BKT-7. Lifecycle rules** enforce retention automatically (Section 10).
- **BKT-8. Access logging** enabled on every bucket (S3 server access logs or CloudTrail data events; Cloud Audit Logs data-access logs for Firebase/GCS) and retained per Section 12.
- **BKT-9. Secrets.** Signing keys and service credentials live in a secrets manager or environment-level secret store, never in source code, client builds, or logs, and are rotated if exposure is suspected.

### 9.3 Signed URL issuance rules

- **URL-1.** A signed URL is generated **on demand**, **after** the backend authorizes the request (role, ownership, or assignment check from T_85ab37). Authorization is evaluated at issue time, every time.
- **URL-2.** One URL grants **one method on one object**: a GET URL cannot write, a PUT URL cannot read, and neither works for another object.
- **URL-3.** PUT URLs are constrained to the expected content type and maximum size.
- **URL-4.** Signed URLs are **never stored** in the database, logs, analytics, or notification payloads (PII-7, CP-3, MED-6).
- **URL-5.** Responses that return a signed URL set `Cache-Control: private, no-store`.
- **URL-6.** Because lifetimes are short, URLs are not revoked individually. After a role change, account deletion, or key rotation, no previously issued URL stays valid for longer than its lifetime, and rotating the signing key invalidates all outstanding URLs immediately.

### 9.4 Signed URL lifetimes

| Purpose | Method | Lifetime | Requested by |
|---|---|---|---|
| Upload report photo (original) | PUT | **10 minutes** | Citizen |
| Upload completion evidence | PUT | **10 minutes** | Cleaning Team member |
| View own sanitized report media | GET | **10 minutes** | Citizen |
| View sanitized media on the dashboard | GET | **10 minutes** | Operator / assigned team |
| View raw original (permitted accounts only) | GET | **5 minutes** | Operator with raw-media permission |
| AI service read | Service identity (preferred) or GET | **5 minutes** if a URL is used | AI service |
| Any public-facing view | — | **No URL issued** | — |

**Hard cap:** no signed URL may be issued with a lifetime above **15 minutes**. Exceptions require a documented security approval. The dashboard and app request a fresh URL whenever a media item is displayed.

**Alignment with ADR-003.** The lifetimes above are the values this specification adopts for ADR-003 alignment. Where ADR-003 defines a different lifetime or mechanism for a given purpose, ADR-003 governs and this table is amended to match.

## 10. Retention and Deletion

The Proposal requires a defined retention period after which non-essential image data is deleted (Section 17). The values below are **provisional defaults, stored as configuration**, and are confirmed during the pilot.

### 10.1 Retention schedule

| Data | Retention | Then |
|---|---|---|
| Raw originals (`raw/`) | **30 days** after upload | Permanently deleted (lifecycle rule) |
| Sanitized report photos and completion evidence | While the report is open, and **12 months** after it is resolved | Deleted |
| Precise coordinates in `REPORTS` | While the report is open, and **12 months** after it is resolved | Irreversibly generalized to the P1 grid so hotspot history remains usable |
| Public coordinates and aggregates | Kept for analytics | — |
| `STATUS_HISTORY`, `ASSIGNMENTS` | Kept (no PII) | — |
| Account data (name, email, contact) | While the account is active | Deleted per 10.3 |
| Security and access audit log | **12 months** | Securely deleted |
| Operational application logs | **90 days** | Securely deleted |

### 10.2 Dataset use (AI training and evaluation)

Using citizen images to fine-tune or evaluate the models (Proposal Sections 13 and 19, locally collected pilot images) requires a **separate, optional, default-off consent** (Section 11). Only **sanitized** images and **public or cell-level coordinates** may enter a dataset. No dataset contains names, emails, user IDs, or descriptions (PII-5). Datasets are versioned, access-controlled, and image entries are removed if consent is withdrawn.

### 10.3 Account and data deletion

- On a deletion request, the citizen's name, email, contact details, push tokens, and authentication record (including the Firebase Authentication record) are deleted **within 30 days**.
- Their reports are **kept as anonymous operational records**: `REPORTS.user_id` is nulled or pointed to a single "deleted user" placeholder, so no link to the person remains.
- Media of those reports is deleted on the normal schedule, or earlier on request if the report is not needed for an open operational task.

### 10.4 Backups

Backups follow the same retention limits and are encrypted. Backups roll off within **35 days**. If a backup is restored, previously processed deletions are re-applied before the system returns to service.

## 11. Consent, Transparency, and Citizen Rights

- **Privacy notice at registration**, in plain language, stating what is collected (photo, GPS, category, description, account details), why, who can see it (operators and assigned cleaning teams), and what appears publicly (coarsened, aggregated data only).
- **Permissions at point of use.** Camera and location permissions are requested when the citizen starts a report, with an explanation.
- **Capture guidance** in the report flow: a short reminder, shown on the existing **Review and submit** step (Proposal Section 16.1, steps 5–6), not to photograph people's faces or license plates and not to put personal details in the description.
- **Optional dataset consent** (Section 10.2) is a separate, default-off choice that can be changed at any time.
- **Citizen rights:** view their own data and report history; correct their account details; delete their account and data (Section 10.3); withdraw consent.
- **Location transparency:** the citizen is told that precise location is used only for routing and handling the report and is not shown publicly.

## 12. Audit Logging and Monitoring

`STATUS_HISTORY` already records status changes (Proposal Section 15.2). This policy adds a separate, **append-only security audit log** for access to sensitive data.

**Events logged:** issuance of any raw-media signed URL; access to precise coordinates in bulk or by export; creation of any dataset or export; role or permission changes affecting data access; failed authorization attempts on reports or media; account deletion and retention purges; manual sensitive-tier flags.

**Fields:** timestamp, actor ID and role, action, object reference (report ID or media ID), result (allowed / denied), and source (client or IP). Logs contain no PII beyond the opaque actor ID (PII-7).

**Protection and retention:** write-once or append-only, readable only by Administrators with authorized access to audit and security records (T_85ab37, Section 10), retained for 12 months.

**Monitoring:** unusual volumes (for example many raw-media requests or precise-coordinate reads by a single account in a short period) and repeated denied requests raise an alert. Thresholds are set during the pilot.

*Note:* this log is an addition to the seven-table schema in Proposal Section 15.2 and is implemented as a separate table or log store.

| V-19 | Check for `getDownloadURL`-style long-lived links | None issued or stored | Critical |
| V-20 | Submit an account deletion request | Name, email, contact, tokens, and auth record removed; reports remain unlinked | High |
| V-21 | Check lifecycle behaviour | No raw originals older than 30 days remain | Medium |
| V-22 | Restore a backup in a test environment | Prior deletions are re-applied | Medium |
| V-23 | Administrator account requests report media, precise coordinates, or a raw original | Denied | Critical |
| V-24 | Administrator opens a user account and the audit log | Allowed only for those purposes, and each access is logged | High |

Any **Critical** failure blocks release.

## 15. Assumptions and Notes

- Numeric parameters (grid sizes, k-threshold, signed URL lifetimes, retention periods, file-size limits) are conservative defaults held in configuration, not hardcoded, and are confirmed during the pilot. This mirrors how the Proposal treats other tunable parameters.
- The design supports either storage option named in the Proposal (Firebase Storage or Amazon S3); service-specific requirements are given for both.
- This is a project-level specification. It is informed by the principles of data minimisation, purpose limitation, consent, and user rights found in personal-data-protection frameworks such as Egypt's Personal Data Protection Law (Law No. 151 of 2020) and the GDPR. It is not legal advice, and a legal review is recommended before any real-world deployment.
